# OKR 示例（2026 Q4）

## 技术经理 · 带团队工程能力（人员管理向）

**角色：** 软件开发技术经理  
**周期：** 2026 Q4（示例）  
**Objective（O）：** **打造可依赖的工程团队：代码质量可控、架构决策清晰、下属能独立交付**

| # | Key Result | 目标值 | 当前 | 状态 |
|---|------------|--------|------|------|
| KR1 | **Code Review 覆盖与时效**：团队合并主干的 PR，有 ≥1 名 reviewer（含你或指定骨干）且 **24h 内** 完成首轮反馈的比例 | ≥ 95% | — | 未开始 |
| KR2 | **架构与重大变更**：本季度 **跨模块 / 新依赖 / 数据与接口契约** 类改动，均有 **简短 ADR 或设计纪要**（含备选方案与回滚）并经你 **签字评审** | 100% 符合清单的变更 | — | 未开始 |
| KR3 | **质量门禁**：团队负责服务的 **P0/P1 线上事故**（因代码/配置/发布流程） | 0 起；若有 1 起则 **7 日内** 完成复盘并落地 1 条防再发措施 | 0 起 | 未开始 |
| KR4 | **人员成长**：每位直接下属完成 **1 次** 你约定的成长项（如独立负责一模块、主导一次 RFC、带新人 CR、分享一次架构/故障复盘） | 100% 下属 | — | 未开始 |
| KR5 | **1:1 与风险前置**：直接下属 **双周 1:1** 完成率；识别出的 **人力/进度/技术债** 风险，**2 周内** 有书面跟进（任务拆分、人力调整或范围裁剪） | 1:1 ≥ 90%；风险跟进 100% | — | 未开始 |

**你可以怎么管（和 KR 对应，不写进 OKR 也行）：**

- **代码：** 定 CR 规范（规模、测试、禁止项）；抽查 + 复盘典型 bad case；难点 PR 你亲自看。  
- **架构：** 大改先 **30 分钟对齐** 再写；小改授权骨干，你只做边界与一致性检查。  
- **下属：** 1:1 谈 **交付、成长、阻塞**；KR4 避免空泛「培训」，要 **可验收的一件事**。

## 软件开发 · 交付与工程质量（业务交付向）

**角色：** 软件开发技术经理 / 研发团队  
**周期：** 2026 Q4（示例）  
**Objective（O）：** **按承诺交付核心产品能力，且主干可发布、质量可度量**

| # | Key Result | 目标值 | 当前 | 状态 |
|---|------------|--------|------|------|
| KR1 | **版本交付**：路线图内 **P0 功能** 按里程碑上线（含 API/前端/后端联调验收通过） | ≥ 100% P0 按期或书面延期说明 | — | 未开始 |
| KR2 | **发布与回归**：生产发布 **回滚演练或蓝绿/金丝雀** 至少 1 次；发布后 **24h 内** 无 P0；CI 主干 **构建通过率** | 演练 1 次；CI ≥ 98% | — | 未开始 |
| KR3 | **测试与缺陷**：新增/改动核心路径 **自动化测试** 覆盖（单测 + 关键集成）；本季度 **生产 P1+ 缺陷** 数较上季 | P1+ 环比下降 ≥ 30%（或 ≤ N 个，自定） | — | 未开始 |
| KR4 | **性能与稳定性**：核心接口 **P99 延迟**、错误率相对基线；**SLO 违约**次数（按团队约定服务） | P99 不劣于基线 10%；SLO 违约 ≤ 2 次/季 | — | 未开始 |
| KR5 | **技术债**：本季度 **关闭** 的 P0/P1 技术债项（性能、安全、耦合、可观测性等，来自 backlog 标签） | ≥ 5 项关闭且有验收说明 | — | 未开始 |

**和「人员管理 O」的分工：** 上一个 O 管 **人、Review、架构过程**；本 O 管 **交付结果、线上质量、工程度量**。两个 O 可同时挂一个季度，对上汇报时各讲一半。

## 写法说明（抄模板时用）

| 要素 | 建议 |
|------|------|
| **Objective** | 定性、鼓舞人心、一个周期 3～5 个为宜 |
| **Key Result** | 可量化、可验收、有截止日期；避免把「做某功能」当 KR，改成 **可度量结果** |
| **状态** | 未开始 / 进行中 / 有风险 / 完成 |
| **对齐** | 每个 O 可注「上级 O#」；KR 不要互相重复 |
